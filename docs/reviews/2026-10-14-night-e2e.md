# Night end-to-end sweep, 2026-10-14

**Setup:** two dev servers peered with each other, run from `casm-ng-main`:
- A: `/tmp/casm-peers-a` on port 7492, peer name `b`.
- B: `/tmp/casm-peers-b` on port 7493, peer name `a`.

Port 7491 was taken by another agent's dev server, so the pair used 7492/7493. The stable service was never touched.

Commands were run with the plain CLI (`CASM_HOME=/tmp/casm-peers-x node packages/cli/src/main.ts`), on each server directly or across through `-H`.

The sweep used real model calls: Claude haiku, Codex `gpt-6-luna`, and an OpenCode free model. pi was not run, because its models are local on fedora.

**Fixed in:** `e257193`, `93af8cd`, `c1456fc`, `1cbb4b1`, `629962b`, `d82c51b`, `e6bd7f3`. Each fix comes with a test. The suite has 173 tests and all pass.

## Findings

### 1. A prompt sent just before a server stop was lost (fixed: `d82c51b`, `e6bd7f3`)

This is the likely cause of the message lost on the Mac.

- **Repro:** `casm run --project p --provider claude "Reply with just: EARLY"`, then stop the server within about 1 s. Start it again.
- **Expected:** the prompt shows up in the agent's history, or in `casm pending`.
- **Actual:** it was in neither. `nativeSessionId` stayed null. Claude had in fact written a session file containing the prompt, but casm never learned its id because the server stopped before Claude's `system/init` message arrived.
- **Why:** `shutdown()` closes the sessions. The resulting `closed` events arrive after the store is closed and the process has exited. Nothing persisted the running turn's prompt, and it only existed in memory.
- **Fix:**
  - Shutdown keeps an unanswered prompt as a pending message with reason `failed` and the note "the server stopped before the agent answered".
  - Provider events that arrive after shutdown are ignored. Before, they threw "database is not open".
  - Claude sessions get their id from casm up front (the SDK's `sessionId` option), so the agent points at its session immediately.
  - A Claude session that was never stored (the server died first, or the file was deleted) starts anew under the same id, with a warning notice. Before, every send failed with "No conversation found".
  - The kept prompt is not resent automatically, because the provider may have stored it. In one live run, the Claude process outlived the server and finished the turn. So at startup, a kept prompt that the agent's history shows as already answered is dropped.
- **Verified live:**
  - Claude finished the turn after the stop: the kept prompt was dropped at the next start.
  - Claude did not finish: `casm pending` lists the prompt, `casm retry <agent> <id> --wait` delivers it, and the history then shows it.

### 2. A turn that failed before any answer dropped its prompt; `wait` exited 0 silently (fixed: `93af8cd`)

- **Repro:** point an agent at a session Claude doesn't have (here by editing `native_session_id`), then run `casm send --wait <agent> "…"`.
- **Expected:** an error, and the prompt kept somewhere.
- **Actual:** exit code 0 and no output. The turn ended `failed` ("No conversation found with session ID …"), and the prompt was in neither history nor pending.
- **Fix:**
  - A turn that fails before the agent produced anything keeps its prompt as a `failed` pending message. "Anything" means an item other than the user's prompt or a notice, a delta, a usage update, or tool output.
  - A failed message is never resent on its own and doesn't hold back later messages.
  - New method `agent.retryPending` (`casm retry <agent> <message-id>`). `casm cancel` removes it.
  - `agent.wait` returns `lastTurn: {outcome, error}`. `casm wait`, `send --wait`, and `run --wait` print the error and exit 5.
  - A failed turn whose agent had answered part of it isn't kept, because the prompt is already in the agent's history.

### 3. Queued messages waited up to 15 s after a restart (fixed: `93af8cd`)

- **Repro:** queue a message behind a running turn, restart the server, then check `casm pending` right away.
- **Expected:** the queued message is sent when the server starts.
- **Actual:** it sat as "idle, 1 pending" until the 15 s timer fired. A new send in that window started first, ahead of the older queued message.
- **Fix:** due pending messages are sent at startup.

### 4. Steered messages were missing from Claude history (fixed: `e257193`)

- **Repro:** `casm send <agent> "…sleep 12…"`, then `casm send --steer <agent> "Change of plan…"`, then `casm history`.
- **Expected:** the steer message appears where Claude absorbed it.
- **Actual:** the transcript jumped from the tool call straight to the reply. Claude stores a mid-turn prompt as an `attachment` line (`queued_command`, `commandMode: "prompt"`) on the parent chain, and `chain()` dropped every attachment line.
- **Fix:** attachments stay on the chain, and `queued_command` prompts become user items.
- **Codex:** records steers as user messages already. Its history was correct.

### 5. `wait` after an interrupt printed an old reply (fixed: `1cbb4b1`)

- **Repro:** start a long turn, `casm interrupt <agent>`, then `casm wait <agent>`.
- **Expected:** no reply (the turn was interrupted).
- **Actual:** it printed "CRON", the reply from several turns earlier, and exited 0. `agent.wait` fell back to the newest assistant item in history whenever the latest turn had no reply.
- **Fix:** the fallback only applies before any turn since the server started. `casm wait` prints "the turn was interrupted".

### 6. `casm shell` exited 0 when the command failed (fixed: `629962b`)

- **Repro:** `casm shell <agent> "exit 3"`.
- **Expected:** a nonzero exit code.
- **Actual:** exit 0, although the history marks the command ✗.
- **Fix:** exit 1 when the user's shell item ends in error. Checked with Claude and Codex, locally and through `-H`.

### 7. Missed schedule runs waited for the first 15 s tick (fixed: `c1456fc`)

- **Repro:** `casm -H b schedule add --at "in 1m" …`, stop B past that time, then start it again.
- **Expected:** the missed run happens once when B is back.
- **Actual:** it did, but only on the first tick, about 15 s after start.
- **Fix:** the scheduler also ticks at startup.
- **Also in this commit:** the schedule list no longer prints the default name next to the target ("→ steer1 … → steer1").

### 8. `casm --json peer list` failed; an empty peer list printed nothing

The Mac agent reported this. The main agent had already fixed it in `4c962de`. Still open: `casm -H b peer list` silently shows this machine's peers. `casm -H b peers` is the command that shows b's peers.

## Worked as expected

- **`run` / `send` / `--wait` / `--steer`:** Claude and Codex, locally and through `-H`. A steer changes the running turn's answer. `send --steer` to an idle agent starts a turn.
- **pending + cancel:**
  - Messages queued behind a running turn are listed in order.
  - `cancel <agent> <id>` and `--all` work. `cancel` without an argument is refused.
  - `interrupt` drops the queue.
  - The agents list shows `pending.count`.
- **Schedules:**
  - `every`, `cron`, and `once` fire on time. `once` disables itself afterwards.
  - `run` works. `--skip-if-busy` skips while the agent is busy; without it, the message is queued.
  - `enable`, `disable`, and `rm` work.
  - A new-agent preset creates "name · time" agents.
  - Schedules on B work driven through `-H b`.
- **Limits and usage:**
  - `casm limits` shows Claude's 5-hour and weekly windows and Codex's windows, also through `-H b`. `--refresh` works.
  - `casm usage` and `agents --usage` work.
- **Subagents across hosts:** the child's parent is `{A's server id, parent agent id, host "casm-dev"}` in all of these cases:
  - Claude with `--casm-tools` calling MCP `create_agent(host: "b")` and then `wait`;
  - Codex with `--casm-tools` doing the same;
  - Claude shelling out to `casm -H b run --wait`.
  - `--parent s1/a1` and `--parent none` also work.
- **Interrupt / reload / restart / archive:**
  - `reload` keeps the native session; the agent remembers earlier turns.
  - `restart` starts a new session; the agent no longer remembers earlier turns.
  - `archive` hides the agent from `agents`; it is shown with `--all`. `send` and `shell` to an archived agent are refused.
- **Restart mid-turn:**
  - Claude, Codex, and OpenCode agents killed mid-turn resume on the next send. Claude closes the interrupted turn with "No response requested."
  - Queued messages survive a restart.
- **Peer disconnect:** while `-H b watch` is running, stopping B makes the watch exit with "lost the connection to host b". A reconnects once B is back.

## Small things not fixed

- `casm usage` for Claude agents read from the store shows `ctx 32k` without the window size. The window is only known from the live session.
- Claude's limit reset times print as `…+00:00` with microseconds, while Codex's print as `…Z`. Both are valid ISO times; the CLI just shows them raw.
- `parent.host` is the parent server's own name ("casm-dev" for both dev servers), not the name the child's server uses for it as a peer. `serverId` is the reliable key; the apps should map it.
- `schedule run` doesn't move `nextRunAt` (as designed), so an `every` schedule run by hand can fire again soon after.
- A steer prompt (`send --steer`) sent into a turn that then dies before answering is not kept. Only the turn's starting prompt is.
